# Feature Specification: ReAct 循环（Agent 大脑）

**Feature Branch**: `002-react`

**Created**: 2026-09-01

**Status**: Draft

**Input**: 需求文档 docs/requirements/002-react.md（主体阶段 US-2 ReAct 循环，核心能力二；课件第17节对齐版）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 想一步、做一步、看结果，直到给出最终答复（Priority: P1）

用户向 Agent 提出一个需要查资料才能回答的问题（如"查一下北京天气并告诉我穿什么"）。Agent 在循环里先想（调模型）、决定去查天气（调工具）、拿到结果再看一眼、最后给出穿搭建议。整个过程不是写死的流程，是 Agent 运行时自己决定的；一次对话里可以连续完成多步骤任务（先读文件、再分析、再调 API、再生成报告）。

**Why this priority**: 这是本节存在的意义——ReAct 循环是 Axion"不做编排"的技术支点，也是 001 未做独立 Demo 的原因（Provider 要和 ReAct 一起才能撑起 Demo 一）。主循环跑通是其他所有边界（审计、纠偏、兜底）依附的骨架。

**Independent Test**: 用测试替身模拟模型"第一轮返回工具调用请求、第二轮返回最终答复"和工具执行，验证一次运行完成两轮循环、工具结果被回填、最终返回答复文本。全程不碰网络，单测秒级跑完。

**Acceptance Scenarios**:

1. **Given** 模型第一轮返回"调用天气工具"的请求，**When** 循环收到该请求，**Then** 工具被执行、结果回填对话，循环继续下一轮
2. **Given** 模型某一轮返回不带工具调用的答复，**When** 循环收到该响应，**Then** 返回该文本作为最终答复，循环结束
3. **Given** 一次对话需要连续完成多个步骤（工具A→工具B→收尾），**When** 用户发起对话，**Then** 循环按模型每轮的决定连续执行，多轮间中间结果累积不丢失
4. **Given** 每轮模型调用，**When** 循环调模型，**Then** 调用携带会话标识，该次调用的审计记录能关联到会话

---

### User Story 2 - 每步工具执行可审计（Priority: P2）

严监管行业要求系统完全可审计。Agent 在循环里每次执行工具——成功或失败——都留一条审计记录：哪个会话、哪个工具、什么参数、什么结果、成败与原因、耗时。审计数据 day one 落库，与模型调用审计同口径，不靠日志反解析。

**Why this priority**: 可审计是 Axion 的核心差异化能力，工具调用是 Agent 对外产生副作用的动作，失败路径的留痕最容易漏——漏掉意味着一次真实事故在系统里完全没有痕迹。

**Independent Test**: 模拟工具执行成功与失败两条路径，验证两条路径都产生审计记录且字段（会话、工具名、参数、结果、成败标志与原因、耗时）正确、可关联到会话。

**Acceptance Scenarios**:

1. **Given** 一次工具执行成功，**When** 执行结束，**Then** 产生审计记录，标记成功，记录参数、结果与耗时
2. **Given** 一次工具执行失败，**When** 执行抛出异常，**Then** 仍产生审计记录，标记失败并记录失败原因，同时异常不吞、结果如实回传

---

### User Story 3 - 出错时自己纠偏（Priority: P2）

工具调用失败时，Agent 能看到失败结果，并在下一轮自己决定重试、换工具还是如实告知用户——而不是把错误直接抛给用户。纠偏是模型下一轮的思考决定，执行层只如实回报结果、不替 Agent 做决定。

**Why this priority**: 真实环境里工具失败是常态（超时、数据缺失），Agent 能自己纠偏是 ReAct 相对固定流程的本质优势；同时"内部不自动重试"是执行权边界，边界错一次就会引入隐式行为、破坏可审计性。

**Independent Test**: 模拟第一轮工具执行失败，模型第二轮改换另一工具并成功，验证失败结果完整回传模型、循环继续、最终答复基于纠偏后的结果。

**Acceptance Scenarios**:

1. **Given** 一次工具执行失败，**When** 结果回传模型，**Then** 模型在下一轮能看到完整失败信息（含是否可重试的标识）并自行决定下一步
2. **Given** 工具执行失败，**When** 执行层处理该失败，**Then** 执行层不自动重试该工具，重试只可能由模型的下一轮思考发起

---

### User Story 4 - 每轮上下文正确组装（Priority: P3）

循环每转一圈，都要把"这个 Agent 是谁（角色设定+引导文件）、今天几号、之前聊到哪（截断后的历史）、现在有哪些工具可用、长期记忆（如已启用）"组装成模型能理解的一份上下文。组装必须每次重读来源文件——用户改了引导文件，下一轮立即生效；显式引用的文件缺失必须报错，引导文件缺失至少警告——静默跳过会造成"人格悄悄丢了"这类最难查的软故障。

**Why this priority**: Prompt 组装质量直接决定 Agent 行为对不对：日期漏了，定时场景的"今天"全错；历史不截断，上下文迟早撑爆；文件缓存，用户的修改永远不生效。

**Independent Test**: 对组装产物断言四部分内容与顺序；改文件后下一次组装立即读到新内容；引用缺失时报错、引导文件缺失时产生警告日志。

**Acceptance Scenarios**:

1. **Given** 一个 Agent 配置了角色设定与引导文件且绑定若干技能，**When** 组装一轮 prompt，**Then** 产物按序包含：角色设定+引导文件内容+技能说明（末尾附当前日期时间）、长期记忆（未启用则跳过该段）、最近若干轮对话历史、可用工具列表（模型可理解的格式）
2. **Given** 对话历史超过 N 轮（默认 20），**When** 组装 prompt，**Then** 只保留最近 N 轮，且截断不切断同一轮内的工具调用链
3. **Given** 组装后引导文件内容被修改，**When** 下一轮组装，**Then** 读到的是新内容（无缓存）
4. **Given** 显式引用的文件不存在，**When** 组装，**Then** 报错；若缺失的是引导文件，至少产生警告

---

### User Story 5 - 统一入口编排 + 防死循环兜底（Priority: P3）

无论消息从哪个入口来（命令行、网页、定时触发），最终都走同一个编排入口：设置当前 Agent 上下文→跑循环→保存会话→清理上下文。即使处理抛异常，上下文也必须清理（否则并发复用时下一个请求会拿到别人的 Agent 配置——这是单请求测试永远测不出来的阴险 bug）。循环有死循环兜底：模型一直要求调工具不收敛时，转满最大轮数（默认 10）强制结束，返回明确的停止文案。

**Why this priority**: 三入口共用引擎是宪法级架构决策（不共用则 ReAct 行为会随入口漂移）；ThreadLocal 泄漏与死循环是两个"平时测不出来、线上才炸"的兜底，必须由测试显式钉死。

**Independent Test**: 验证处理期间工具执行能取到当前 Agent 上下文、处理结束（含异常）后上下文必为空、会话被保存；模拟模型永不收敛，验证恰好转满最大轮数强制停止并返回"达到最大轮数"文案。

**Acceptance Scenarios**:

1. **Given** 一次会话处理开始，**When** 循环或工具执行期间，**Then** 能取到当前 Agent 的配置
2. **Given** 处理过程中抛出异常，**When** 异常冒出，**Then** 当前 Agent 上下文仍被清理，异常继续上抛
3. **Given** 一次处理结束，**When** 循环返回，**Then** 累积了完整历史的会话被保存
4. **Given** 模型每一轮都要求调工具、永不收敛，**When** 循环达到最大轮数（默认 10），**Then** 强制结束并返回含"达到最大轮数"的停止文案，模型恰好被调用最大轮数次、一轮不多

---

### User Story 6 - 沙箱接口墙先行（Priority: P3）

涉外操作（文件、Shell、HTTP）将来必须过安全校验。本节先把校验的接口立起来：一个方法、四种动作类型、违规抛特定异常。本节无人调用、无白名单实现——先把墙的位置定死，后续各工具接入时接口不变。

**Why this priority**: 接口先行是安全地基的宪法要求——接口定了，后续升级隔离方案（白名单→容器）不用改任何调用方；晚立接口则每个工具都要返工。

**Independent Test**: 定义层面验证：接口只有一个校验方法、动作类型恰为四种、存在违规异常类型；编译与静态检查通过。

**Acceptance Scenarios**:

1. **Given** 一个涉外动作（读文件/写文件/执行命令/发请求之一），**When** 交给校验接口，**Then** 接口按动作类型放行或抛违规异常（本节仅定义契约，具体白名单行为由后续能力交付）

---

### Edge Cases

- 模型每一轮都要调工具、永不收敛 → 转满最大轮数（默认 10）强制停止，一轮不多（死循环兜底）
- 对话历史超过 N 轮 → 截断只留最近 N 轮，且不切断一轮内的工具调用链（上下文撑爆）
- 工具执行失败 → 审计记失败与原因、异常不吞、结果带重试标识回传
- 处理抛异常 → 当前 Agent 上下文也必须被清理（并发复用串号风险）
- 显式引用的文件缺失 → 报错；引导文件缺失 → 至少警告
- 长期记忆未启用 → prompt 的长期记忆段跳过
- 工具列表为空 → 循环照常运行（模型无工具可调则直接答复）
- 审计表结构测试必须用与生产一致的手工建表脚本执行（不依赖自动建表——否则测试绿了、生产对不上）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 自实现 ReAct 主循环：追加用户消息→组装 Prompt→调模型（携带会话标识）→无工具调用则返回最终答复→有则逐个执行并把结果回填→回到组装继续循环。MUST NOT 触发框架的自动工具执行——工具执行只此一条路
- **FR-002**: 模型某一轮不请求调用工具时，循环 MUST 返回该轮文本作为最终答复；模型持续请求工具不收敛时，MUST 转满最大轮数（默认 10，可由 Agent 配置覆盖）强制结束，返回含"达到最大轮数"的停止文案
- **FR-003**: 每轮模型的响应与工具执行结果 MUST 累积进会话（顺序对位），下一轮接得上、事后可审计
- **FR-004**: 每轮 Prompt MUST 按序组装四部分：① 角色设定+引导文件内容+已绑定技能说明，末尾附当前日期时间 ② 长期记忆（未启用则跳过）③ 最近 N 轮对话历史（默认 20，超出截断且不切断一轮内的工具调用链）④ 可用工具列表（模型可理解的格式）
- **FR-005**: 组装时 MUST 每次重新读取来源文件、不缓存；显式引用的文件缺失 MUST 报错；引导文件缺失 MUST 至少产生警告——不得静默跳过
- **FR-006**: 工具执行 MUST 收口在唯一执行点：按名找到工具→执行→结果包装→写审计记录。成功与失败 MUST 都写审计（会话、工具名、参数、结果、成败标志与原因、耗时）；失败时异常不吞，结果带重试标识回传；执行层 MUST NOT 自动重试
- **FR-007**: 系统 MUST 提供统一的会话处理编排入口（三种触发源共用）：设置当前 Agent 上下文→跑循环→保存会话→清理上下文
- **FR-008**: 当前 Agent 上下文 MUST 在处理结束（含异常路径）后被清理；处理期间工具执行可读取当前 Agent 上下文
- **FR-009**: 系统 MUST 交付最小会话契约：会话数据结构（对话历史累积容器、可序列化）+ 会话管理器最小契约（按渠道+用户+Agent 名取或建、读取、保存）；会话标识 MUST 只在会话管理器内一处拼接
- **FR-010**: 系统 MUST 交付沙箱校验接口：单方法校验、四种动作类型（文件读/文件写/命令执行/网络请求）、违规抛特定异常——本节仅定义契约，无实现、无白名单配置、无人调用
- **FR-011**: 全程 MUST 保持同步阻塞调用模型（并发由底层虚拟线程承载），MUST NOT 引入异步编程模型
- **FR-012**: 每次模型调用与工具调用 MUST 记录结构化日志（与审计落库并存，日志不等价于审计）
- **FR-013**: 主循环 MUST 只做调度（转圈、判断停不停、攒结果）——拼 prompt、调模型、执行工具全部交给各自职责组件

### Key Entities *(include if feature involves data)*

- **Session**：一次会话——对话历史累积容器（历史以消息对象承载、可序列化）；标识由渠道+用户+Agent 名生成
- **ToolResult**：一次工具执行的结果——成功标志、内容、错误信息与可重试标识（001 已定义，本节成为循环中的回填物）
- **ToolInvocation 记录**：一次工具调用的审计记录——会话、工具名、参数、结果、成败与原因、耗时（新表，day one 落库）
- **Prompt**：每轮组装产物——角色设定与引导、日期时间、长期记忆（可选）、截断后的历史、工具列表
- **ProfileContext**：当前处理的 Agent 上下文——处理期间供工具执行读取，处理结束必须清理
- **SandboxAction**：一个涉外动作的校验请求——动作类型（文件读/文件写/命令执行/网络请求）与目标

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 多轮工具调用任务一次对话内完成——自动化测试 100% 覆盖两轮以上循环、历史正确累积、正常终止
- **SC-002**: 工具调用审计可追溯率达到 100%——成功与失败两条路径都有记录且可关联到会话
- **SC-003**: 死循环兜底有效——模型永不收敛时恰好转满最大轮数（默认 10）强制停止，一轮不多
- **SC-004**: Prompt 组装四部分内容与顺序、历史截断、文件改动立即生效、缺失报错——全部由自动化测试钉死
- **SC-005**: 处理异常后 Agent 上下文必被清理——由自动化测试钉死（含并发复用场景的守护语义）
- **SC-006**: 验收 Demo 一（每日天气）对话版用真实模型从头到尾跑通一次（人工验收；天气工具就位前可先用最小临时工具验证循环）

## Assumptions

- 前序 001 已交付并被直接依赖：统一模型调用入口（含会话标识参数与模型调用审计）、Agent 配置体系（角色设定、最大轮数、历史截断轮数等运行参数）、消息与工具契约、工具列表翻译能力、手工建表脚本同口径
- 本模块引入底层框架的纯数据模型（Prompt/响应/工具调用），边界为"可用其纯数据模型、禁用其 Agent 抽象与自动工具执行"——此边界已拍板，宪法原则不变
- 本节交付物全部不碰网络：模型、工具均可用测试替身模拟，自动化验收全为单测、秒级跑完；真模型验证在人工部分
- 工具执行权唯一在执行点；沙箱校验由各工具在执行首行自行接入（后续能力起），本节只立接口
- 会话持久化表、命令行通道、工具注册完整形态、内置工具、沙箱白名单实现、长期记忆实现、通知与定时触发均属后续能力，本节只留拼接位或最小契约
- 明确不做：工具并行调用、Agent 间互相委托、流式输出、上下文压缩、执行层自动重试、故障自动切换、认证/限流/RBAC（均已在 001 或本节需求文档明确划出）
