# Feature Specification: Agent Provider 模块（对接 LLM）

**Feature Branch**: `001-provider`

**Created**: 2026-08-30

**Status**: Draft

**Input**: 需求文档 docs/requirements/001-provider.md（主体阶段 US-1 对接 LLM，核心能力一）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多 Provider 并存、按配置路由（Priority: P1）

企业同时采购多家模型服务。底座管理员在全局配置里声明多个 Provider（每家一个唯一名字），Agent 作者在自己的配置里指名用哪家。运行时，调用精确路由到被指名的 Provider，两个 Agent 用两家模型互不干扰；引用不存在的 Provider 名必须当场报错，不能悄悄用错。

**Why this priority**: 这是 Provider 模块存在的根本价值——企业多模型并存是硬需求，"显式映射、不靠扫描"是本节最核心的架构决策，也是后续所有能力（ReAct 循环、Demo 一）的地基。

**Independent Test**: 配置两个 Provider（如 deepseek 与 kimi）并用测试替身模拟两家模型，发起两次分别指向不同 Provider 的调用，验证各自命中、互不串扰，且引用不存在名字时得到清晰报错——不依赖真实模型网络即可完整验证。

**Acceptance Scenarios**:

1. **Given** 全局配置声明了 deepseek 与 kimi 两个 Provider 且凭证走环境变量占位，**When** 一个 Agent 的配置指名 provider=deepseek 并发起对话，**Then** 调用被路由到 deepseek，返回统一结构的响应
2. **Given** 同上配置，**When** 另一个 Agent 指名 provider=kimi 并发起对话，**Then** 调用被路由到 kimi，与 deepseek 的调用互不干扰
3. **Given** 一个 Agent 的配置引用了全局层不存在的 provider 名，**When** 启动加载该配置或发起调用，**Then** 系统给出清晰报错，不得静默使用错误模型或留空跑过
4. **Given** 模型调用返回了"想调用某工具"的请求，**When** 上层拿到响应，**Then** 响应中原样携带该工具调用请求，Provider 层不代为执行

---

### User Story 2 - 每次模型调用可审计（Priority: P2）

严监管行业要求系统完全可审计。每次模型调用——无论成功还是失败——都留下一条审计记录：哪家 Provider、哪个模型、多少 token、耗时多久、结果如何，并且能关联到发起这次调用的会话。审计数据从第一天就落库，而不是先靠日志、后期再反解析。

**Why this priority**: "可审计"是 Axion 的差异化卖点，审计数据的地基必须 day one 立起来；失败路径的留痕最容易漏，漏掉意味着一次真实事故在系统里完全没有痕迹。

**Independent Test**: 用测试替身模拟模型调用成功与失败两种路径，验证两种情况下都产生审计记录，且字段（Provider、模型、token 用量、耗时、成功/失败标志与原因）正确、可关联到会话。

**Acceptance Scenarios**:

1. **Given** 一次模型调用成功返回，**When** 调用结束，**Then** 产生一条审计记录，包含 Provider 名、模型名、token 用量、耗时，并标记为成功
2. **Given** 一次模型调用失败（超时、限流、模型报错），**When** 调用抛出异常，**Then** 仍产生一条审计记录，标记为失败并记录失败原因，同时异常继续抛给上层处理
3. **Given** 一次调用发生，**When** 事后查阅审计记录，**Then** 该记录能关联到发起这次调用的会话

---

### User Story 3 - 工具能力可翻译、不执行（Priority: P3）

模型具备"调用工具"的能力：调用前系统把可用工具及参数要求告诉模型，模型可能回应"想调某工具"。Provider 层负责把工具说明翻译成模型看得懂的格式，并把模型的调用请求原样带回——真正执行工具的是上层循环，Provider 全程只翻译、不执行。

**Why this priority**: 工具调度与沙箱检查的执行权必须攥在系统自己手里。若底层框架替系统自动执行工具，工具会被调两次且绕过安全检查——这是本模块最容易埋 bug 的一条边界。

**Independent Test**: 构造一个带参数说明的工具，验证翻译产物的字段与工具定义一一对齐、产物中不含任何执行逻辑；模拟模型返回工具调用请求，验证请求被原样透传而非执行。

**Acceptance Scenarios**:

1. **Given** 一个 Agent 可用若干工具且各自带参数说明，**When** 发起模型调用，**Then** 工具以模型能理解的格式随请求发出，参数说明字段一一对齐
2. **Given** 模型回应"想调用某个工具"并给出参数，**When** Provider 层拿到响应，**Then** 该请求被原样交回上层，不发生任何实际执行
3. **Given** 底层框架具备自动执行工具的机制，**When** 本模块发起调用，**Then** 该自动执行机制被显式关闭（回归测试守护，一旦改回自动执行测试立即失败）

---

### Edge Cases

- 全局配置缺失或非法（Provider 无名字、API key 占位缺失）时，启动校验给出清晰报错，不静默失败
- 环境变量占位符在运行时解析不到实际值时，报错信息指明缺失的变量名
- 模型调用失败（超时、限流、模型报错）时，错误如实抛给上层，不做静默重试或降级
- 同一 Agent 配置里 model 名与 Provider 不匹配时，交由 Provider 端返回错误并如实上报
- 工具清单为空时，调用正常进行且请求中不带工具内容
- 单个 Agent 的配置文件损坏时，该 Agent 加载失败并记录错误日志，不阻断其他 Agent 与整体启动

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持在全局配置中声明多个 Provider，每个 Provider 有唯一名字、密钥（环境变量占位，不允许明文）、模型默认项与可选接入地址
- **FR-002**: 系统 MUST 区分两层配置职责——全局层决定"连不连得上"（有哪些 Provider、凭证从哪来），Agent 层决定"这个 Agent 怎么用"（用哪家、哪个模型、什么温度）
- **FR-003**: 系统 MUST 维护 Provider 名到具体模型对象的显式映射表，按名精确路由；MUST NOT 靠扫描容器中的模型对象集合来区分 Provider
- **FR-004**: Agent 配置引用的 Provider 名在全局层找不到时，系统 MUST 直接报错，不得悄悄用错或留空跑过
- **FR-005**: 系统 MUST 提供统一的调用入口，按 Agent 配置完成一次模型调用并返回统一结构的响应（文本、工具调用请求、token 用量）
- **FR-006**: 每次模型调用——成功和失败都——MUST 写入审计记录：Provider、模型、token 用量、耗时、成功/失败标志与失败原因，并关联发起调用的会话
- **FR-007**: 调用失败时系统 MUST 把异常继续抛给上层处理，不得吞掉（审计留痕与异常上抛两者都要）
- **FR-008**: 系统 MUST 支持把内部工具（含参数说明）翻译成模型能理解的工具格式，翻译只做格式转换、不含执行逻辑
- **FR-009**: 系统 MUST 禁用底层框架的自动工具执行机制——模型返回的工具调用请求只透传、不执行
- **FR-010**: Agent 配置 MUST 支持派生为运行时配置对象并注册内存索引，加载时做合法性校验；坏的配置不阻断整体启动但记录错误日志
- **FR-011**: 全程 MUST 保持同步阻塞的调用模型（并发能力由底层虚拟线程承载）

### Key Entities *(include if feature involves data)*

- **Provider**：一家模型服务接入的声明——名字、凭证来源、默认模型；名字是全局唯一标识
- **Profile**：一个 Agent 的运行时配置——身份、所用 Provider（名字/模型/温度）、可用工具、渠道、定时计划、引导文件与运行参数
- **Message**：一次对话消息——角色、文本内容、工具调用请求与结果
- **Tool**：Agent 可用的一个工具——名字、用途说明、参数要求（本节只交付抽象与翻译，工具实体归后续能力）
- **LLM 调用记录**：一次模型调用的审计记录——会话、Provider、模型、token 用量、耗时、成功/失败与原因

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 两个 Provider 并存时，按名路由互不串扰——路由正确性由自动化测试 100% 覆盖（含"引用不存在名字必须报错"与"自动执行已关闭"两条回归守点）
- **SC-002**: 模型调用的审计可追溯率达到 100%——成功与失败两种路径都有记录且可关联到会话
- **SC-003**: 新增一家 Provider 只需改全局配置与 Agent 配置，不触碰任何调用方代码
- **SC-004**: 至少跑通两家真实模型服务的接入（自动化验收要求两家，受密钥条件限制时至少一家真实跑通、另一家留待办）

## Assumptions

- 工程地基已就位：多模块工程骨架、JDK 21 运行时、结构化日志与静态检查门禁，本节不重复搭建
- 模型服务的接入底层复用 Spring AI Alibaba 的协议转换能力，本节只做薄包装（本模块是底座的一部分，不属于"给非技术用户看的业务功能"）
- 凭证以环境变量注入运行环境，配置文件中只有占位符
- 底层框架与各家模型依赖的确切可用性以项目锁定的版本为准，动手前先核实（依赖存在性是硬前提）
- 接入真实模型服务时网络可达其端点；两家真实跑通取决于密钥齐备（缺一家时先跑通一家并记录待办）
- 本节不做：故障自动切换、并发抢答、熔断、动态路由、成本看板、认证/限流/多租户、流式响应——均属后续扩展阶段
