## 三、各段写作约定

### 背景与价值
- 回答"为什么做"：锚在需求不动摇（调研的定位论证）→ 本模块在五大能力里的位置（技术方案 §2 关系）
  → 关键决策与坑（技术方案 §1.1 / 宪法）→ 与前序课的关系（本课把前序积木拼成什么）。
- 3~6 段，每段带来源引用。

### 用户场景
- 3~5 个。第一个必须是**本节验收场景**（对应 Demo 的对话版/完整版），
  其余从需求文档"基于这个能力可以做的事"和典型场景挑选，每个落到具体动作。

### 功能需求
- 表格四列：`编号 | 需求 | 交付物（落位模块） | 来源`。编号 FR-1..N、NFR-1..N（NFR 放表尾）。
- 段首引子：`> 从课件……部分提炼：编程指南 §…（任务大类）、技术方案 §…。**交付物列是本节
  对外概念的白名单**，清单之外的新增对外概念必须停下报告。`
- **交付物列是白名单**——每个 FR 必须点出具体类/表/配置键 + 落位模块；
  这列是后续 oryx-spec 停止清单第 1 条的判断基准，不能写"相关组件"这种模糊词。
- 来源列精确到章节；"为实现级明确"的补充要显式标注（如"（……为实现级明确）"）。
- 每个**点过名的坑**必须在需求正文里加粗点出并**编号命名**（坑一/坑二/…，命名沿用课件的
  命名，课件没有的自编）——验收标准的测试表据此逐一对号（坑N回归）。
- 末尾按序附三块：**核心代码骨架**（与课件一致的方法签名 + 逐行要点注释——骨架是签名级
  契约，不是实现）、**本节交付物清单**（代码 / 测试 / 表 / 约定四类，照课件"本节交付物"
  格式——这是 oryx-spec 交付清单比对与停止清单第 1 条的判断基准）、**配置形态示例**
  （只展示本模块新增配置键，无新增则注明"本节无新增配置键"）。

### 明确不做
- 段首引子注明来源：需求文档「核心阶段不做」+ 技术方案「核心阶段不做」+ 编程指南边界说明。
- 两类分开列：**扩展阶段不做**（引需求文档 §6.x）与**后续课不做**（引编程指南 §4.x，
  标注"归 US-n"）；前序课已定的不做项标注"本节不翻案"。

### 验收标准
- **自动化部分**：① 引用需求文档 §13 对应的验收点原文；② 测试分层**对齐课件 harness**——
  课件说"全单测不碰网络"就全单测（真模型验证挪人工部分），课件有集成冒烟（如第16节
  `ProviderSmokeIT`）才设 `@Tag("integration")` 冒烟、CI 跳过；③ 测试类表
  （`测试类 | 关键回归点`），**功能需求里每个点过名的坑必须有一条回归测试对号**（坑N回归），
  测试类清单以课件 harness 为基准，缺的表级验证沿用课程既有模式补齐（如 RepositoryTest）；
  ④ 把课件"最值钱的回归测试"以完整代码形态收录（关键断言直接可抄）；⑤ 跑法命令。
- **人工部分**：回答"做完怎么验"——Demo 真跑步骤（从 init 到对话的具体操作）、
  落库核对（打开 oryxos.db 核哪张表哪几列）、反例验证（破坏一个条件看系统如实拒绝）、
  人工 review 关键点（本课最该盯的几段代码）、幂等/边界行为验证。

### 依赖与假设
- **前序交付物**：逐项列出前序课的公共接口/数据/审计口径，标注来源文档与编号；
  结尾必须附"现状确认"——本课相关模块当前是否空壳、表是否已建（实测结果，不照抄假设）。
- **前序缺口（H0 依赖检查）**：课件假定已存在、但仓库实测没有的依赖（如 Session 归后节
  却被本节引用），单独列出并标注"实施前必须先处理"——这是设计文档必报项，不得跳节自造。
- **外部依赖与假设**：框架边界（如 Spring AI 只用两件事的延续）、运行时环境（环境变量、
  网络可达性）、已知留白（如内存版语义）、**跨节契约**（本节交付物是后续哪些课的调用
  契约，后续节不得改动已验收行为）、**跑通标准**（本节撑起哪个 Demo 的哪一版）。

## 四、方案流程图约定（每个设计文档必配，用户 2026-09-04 要求）

**总原则**：图必须与方案描述逐条对齐——图里出现的类名、口径、坑编号、拍板结论必须与 FR 表/
修订说明逐字一致，图与文档不得出现两套说法；图是给未来学员看的，自足可读。001~004 四张
`docs-*-flow.svg` 是事实基准。

### 产出与落位

- 每份设计文档必配一张主流程图；命名 `docs-<slug>-flow.svg`——**区别于技术方案的
  `docs-<slug>.svg`，不得覆盖技术方案既有图**（设计文档图与技术方案图层次不同：前者含坑对号、
  拍板细节、跨节契约，互补不冲突）
- **双版本**：`docs/images/`（浅色）+ `website/public/images/`（深色，网站用）各一份，同名同
  geometry、只换配色
- 设计文档中引用 website 路径 `../../website/public/images/docs-<slug>-flow.svg`，带一句描述性
  caption（图讲什么）；插入位置：FR 表之后、核心代码骨架之前

### 内容要素（按方案实际内容取舍，方案没有的不硬画）

1. **主链路/主流程**：按 FR 顺序的主流程（004：四步执行顺序钉死；002：调度循环 + 回环箭头）
2. **数据源/配置源侧栏**：表、注册表、装配处显式映射等（如 notify_channels 表 → Registry → 步骤①）
3. **失败路径**：方案有"不静默/明确报错"要求时，失败路径框必画（含审计落 success=false）
4. **扩展阶段/后续节归属**：明确不做项以灰色虚线框标注（"扩展阶段（只加不改）""归第 20 节"）
5. **审计条**：涉及 day one 审计的方案，底部粉色审计条写明落账口径（成功记什么、失败记什么）
6. **坑对号**：功能需求中点过名的坑必须在图里标注（坑一/坑二/…，与文档编号一致）
7. **拍板结论与宪法条目**：拍板后的口径与宪法编号直接写进图（如"唯一渠道才缺省（拍板）"
   "宪法 III 哲学"）

### 风格基准

- 以 `docs/images/docs-notify.svg` / `docs-sandbox-flow.svg` 为基准：深色标题条（一句话点出图
  主旨）、Arial、marker 箭头、feDropShadow 投影、rx 圆角
- 配色分工：amber=入口/用户侧、green=本方案核心组件、purple=接口/编排、blue=表/存储/JPA、
  slate=辅助组件、gray 虚线=外部世界/扩展/未来、pink=审计与失败
- 深色版配色对照 `website/public/images/docs-notify.svg`（geometry 不变只换色：bg #0e1420、
  标题条 #d7e2f2 深字、分区深底浅字）

### 防遮挡与几何自检（2026-09-06 沉淀，005/006 流程图遮挡修复实录）

> 遮挡根因归纳：**文字溢出框体**（框宽不够/框高不够）与**箭头几何错误**（终点聚点/起点悬空）。
> 每张图交付前逐条自检，机器可验，不要靠"目测还行"。

1. **文本宽必须小于框宽**：按字号估算文本宽度——CJK 字符 ≈ `font-size × 1.0`px/字、latin 字符 ≈
   `font-size × 0.58`px/字（10px bold latin ≈ 5.8px/字、8px latin ≈ 4.6px/字，实测值）。规则：
   `框宽 ≥ 文本估算宽 + 16px 左右边距`。踩坑实录：「SaveMemoryTool / RecallMemoryTool」
   （34 latin ≈ 197px）溢出 190 框、「LongTermMemoryStore 接口」（103px）溢出 90 框——宽不下就
   改文案或加宽框，**不得默认"应该放得下"**。
2. **框高必须装下行数**：`框高 ≥ 首行基线 15px + 每增一行 +14px + 下边距 ≥ 4px`（8px 字号口径）；
   最后一行文字基线 ≤ 框底 − 4px。踩坑实录：30 高框装两行 8px 字，第二行基线 484 超出框底 482。
3. **多条箭头进同一框时，终点沿框边错开 ≥ 15px**：不得聚于同一点——三个箭头尖叠在
   `(228,163/165/167)` 三个相邻坐标上就是遮挡（005 实录）。
4. **箭头起点必须落在源框边缘上**：起点 x/y 必须在源框的坐标区间内，禁止悬空起点（006 实录：
   起点 `(420,82)` 不在任何框上，视觉凭空冒线）。起点取源框边的中点或上/下 1/3 处。
5. **对角线箭头做穿越检查**：对角箭头要验算路径不穿过任何其他框——在两端点间按 y 插值求 x，
   确认对每个框都不存在「x 在其 x 区间内且 y 在其 y 区间内」的穿越点；验算不过就改曼哈顿折线。
6. **双版本几何一致性**：浅/深两版本**geometry 与文案逐字节一致、只换颜色**；任何改动两个副本
   必须同改。交付前 `diff docs/images/<name>.svg website/public/images/<name>.svg`——输出只允许
   出现颜色值行（fill/stroke/标记），出现几何行差异即为漏改。
7. **交付前自检清单**（按上述 1~5 逐框逐箭头核对，两版本各跑一遍 diff）：框——文本宽/行数/
   末行边距；箭头——起点接边/终点错开/路径不穿框。

## 五、通用纪律

1. **来源两级**：四份 docs 文档 = 权威设计源；课程课件（docs/class/ 对应节）= 实施级事实源。
   不引用 specs/ 产物；运行时环境事实沿用前序文档已述，新增的标记"为实现级明确"。
2. **课件与四文档（或宪法）冲突 → 停下报告等用户拍板，不得自行仲裁**；拍板结论写入
   文档头部「修订说明」。
3. **四文档与课件之外的新增对外概念（新表/新配置键/新类/新模块）→ 停下报告**，不得先斩后奏。
4. **语言**：中文、直接断言（"必须/不得/不做"），关键约束加粗，每段带来源引用；
   不写"可能/建议"式模糊表述；四文档内部的冲突取舍必须显式写出依据（较新文档优先）。
5. **编号**：新序列下一个可用序号；`001-react-runtime` 是历史产物不计入。
6. **成文后报告**：产物路径 + 「为实现级明确」清单 + 冲突拍板记录 + 前序缺口（如有）
   + 下一步 `/oryx-spec NNN-slug`。

## 六、Agent prompt 工具调用约定（2026-09-05 沉淀，005-tool 天气 Demo 实证）

> 适用：设计文档涉及 Agent 使用内置工具（http_get/notify/shell 等）的场景时，用户场景的
> Agent 配置示例（`identity.prompt` 与正文）必须按本节三件套写。

**问题**：模型（尤其 DeepSeek 类）对"通用 HTTP 工具"缺乏"我能用它"的认知——会以"我无法
联网""凭经验回答"等说辞拒绝调用工具（005-tool 人工验收实拍：前两版 prompt 均被拒绝，
日志 `含工具请求=false`）。工具注入与调度链路本身是通的（notify 用例证明），缺的是 prompt
层面让模型相信自己手里有工具。

**三件套（缺一不可，实证有效）**：

| 要素 | 写法 | 作用 |
|------|------|------|
| ① 具体调用示例 | 给工具的**参数级示例**（如 `http_get 的 url 参数填 https://wttr.in/城市?format=3`） | 把抽象工具翻译成模型能想象的具体动作 |
| ② 能力断言 | "你拥有 X 工具，这就是你的 Y 能力"（如"你有 http_get 工具，这就是你的联网能力"） | 对冲模型默认的"我不能联网"认知 |
| ③ 负面禁止 | "禁止声称无法联网""禁止凭经验或猜测回答" | 封死最省事的错误路径，逼它走工具路径 |

**配套约定**：

- 工具调用型 Agent 的 `temperature` 建议 0.3（天气/日报等确定性任务不需要创造性，降低随机
  性提高工具遵循度；005 天气 Agent 已落地）
- 单次成功 ≠ 稳定——新 Agent 至少连续两次人工验证通过才算稳（Demo 钟推版天然提供复验点）
- 失败重试不需要教：ReAct 循环把失败结果喂回模型后，模型会自行换参数重试（005 实拍 4 轮
  重试成功）——prompt 只需第 ④ 条"查询失败时如实说明失败原因，不要编造数据"兜底
